## 1. 개요

### 1.1 목적
친구들끼리 하는 League of Legends 내전(커스텀 게임)을 관리한다. 참가자를 등록하고, 경기 결과를 기록하고, 쌓인 전적을 바탕으로 실력이 비슷한 두 팀을 나눠 준다.

### 1.2 사용자
| 사용자 | 설명 |
|---|---|
| 운영자 | 내전을 여는 사람 1명. 모든 기능을 사용한다. 로그인은 없다. |

### 1.3 범위
| 포함 | 제외 (향후 검토) |
|---|---|
| 플레이어 등록, 조회, 수정, 삭제 | 로그인과 권한 |
| 경기 결과 기록, 조회, 삭제 | Riot API 연동 (티어, 전적 자동 수집) |
| 플레이어별 전적 (승률, 포지션별 승률, 최근 경기) | 챔피언, KDA 기록 |
| 승률 기반 팀 나누기 (포지션 배치 포함) | 경기 결과 수정 (삭제 후 다시 기록으로 대체) |

### 1.4 용어
| 용어 | 뜻 |
|---|---|
| 플레이어 | 내전에 참가하는 사람. 라이엇 ID로 구분한다. |
| 경기 | 내전 한 판. 블루팀 5명과 레드팀 5명이 뛰고, 한 팀이 이긴다. |
| 참가 기록 | 어떤 플레이어가 어떤 경기에서 어느 팀, 어느 포지션으로 뛰었는지에 대한 기록 |
| 포지션 | TOP, JUNGLE, MID, ADC, SUPPORT |
| 티어 | 솔로 랭크 티어 (아이언 ~ 챌린저, 언랭) |
| 레이팅 | 내전 보정 승률. 3.3 참고 |
| 전력 점수 | 팀 나누기에 쓰는 플레이어 점수 (티어 + 레이팅 보정). 3.3 참고 |

## 3. 업무 규칙

### 3.1 플레이어
- 라이엇 ID는 `이름#태그` 형식을 권장하지만 형식을 강제하지는 않는다. 앞뒤 공백은 저장하기 전에 지운다.
- 주 포지션과 부 포지션은 같아도 된다. 부 포지션이 없으면 비워 둔다.

### 3.2 경기
- 한 경기에는 정확히 10개의 참가 기록이 있다. 각 팀에 포지션별로 한 명씩이다.
- 참가 기록의 승패는 저장하지 않고 `참가 팀 == 승리 팀`으로 판단한다.

### 3.3 전력 점수 (팀 나누기용)
- 티어 점수: 아이언 1, 브론즈 2, 실버 3, 골드 4, 플래티넘 5, 에메랄드 6, 다이아몬드 7, 마스터 8, 그랜드마스터 9, 챌린저 10
  - 언랭과 티어 미입력은 그날 참가자 중 티어가 있는 사람들의 평균 점수로 계산한다. 아무도 없으면 골드(4)로 본다.
- 레이팅 = `(승 + 1) / (경기 수 + 2)` (내전 보정 승률)
  - 경기가 없는 신규 플레이어는 0.5(50%)에서 시작한다.
  - 경기 수가 적을 때 1승 0패가 100%로 튀는 것을 막는다.
- **전력 점수 = 티어 점수 + (레이팅 − 0.5) × 4**
  - 내전 성적이 티어를 최대 ±2단계만큼 보정한다는 뜻이다. 내전을 안 했으면 티어 점수 그대로다.
- 팀 전력은 팀원 5명 전력 점수의 합이다.

### 3.4 팀 나누기 알고리즘
1. 10명을 5명씩 나누는 모든 경우(126가지)를 계산한다.
2. 경우마다 각 팀 안에서 포지션 적합도가 가장 높은 배치를 찾는다. 주 포지션이면 2점, 부 포지션이면 1점, 그 외는 0점이다.
3. 경우마다 불균형 점수를 계산한다: **불균형 = 전력 차이 + 0.5 × 티어 분포 차이**
   - 전력 차이: 두 팀 전력 합의 차이
   - 티어 분포 차이: 각 팀 티어 점수를 높은 순으로 세워 1등끼리, 2등끼리 … 5등끼리 뺀 차이의 합. 합이 같아도 "다이아 둘 + 아이언 둘" 대 "골드 넷"처럼 구성이 다르면 커진다.
4. 불균형이 **가장 작은 값 + 0.5** 이내인 경우 중에서 두 팀 포지션 적합도 합이 가장 높은 경우를 고른다.
   - 실력 균형을 먼저 보고, 비슷하면 포지션이 잘 맞는 쪽을 택한다는 뜻이다.
5. 블루와 레드는 임의로 정하지 않고, 첫 번째 그룹을 블루로 한다.

### 3.5 랜덤 교체 (라인별로 맞바꾸기)
1. 균형 결과(3.4)에서 같은 포지션끼리 두 사람을 짝짓는다 (라인 매치업 5쌍).
2. 5쌍 각각 바꿀지 말지 정하는 조합 중, 하나도 안 바꾸는 것과 5쌍을 다 바꾸는 것(블루/레드 이름만 뒤집힌 같은 팀)을 뺀 30가지를 만든다. (2026-11-25: 처음에는 1~2쌍만 바꿨으나 사용자 요청으로 5쌍 모두 대상으로 변경)
3. 불균형 점수(3.4)가 원래보다 **2 이하**로 늘어나는 조합만 후보로 남긴다. 후보가 3개보다 적으면 불균형이 작은 순으로 3개를 후보로 쓴다.
4. 후보 중 하나를 무작위로 고른다. 무작위 값(seed)은 주소에 들어가서, 새로고침해도 같은 결과가 나온다.
5. 같은 라인끼리 바꾸므로 모두 자기 포지션은 그대로이고 포지션 적합도도 변하지 않는다.

## 4. 비기능 요구사항
| ID | 요구사항 |
|---|---|
| NFR-01 | 서버가 HTML을 만들어 보낸다 (Spring MVC + Thymeleaf). 별도 프론트엔드 빌드는 없다. |
| NFR-02 | 데이터는 H2 파일 DB(`./data/inhouse`)에 저장해서 서버를 재시작해도 유지한다. |
| NFR-03 | 저장, 수정, 삭제는 POST로 처리하고, 처리 후 redirect해서 새로고침해도 중복 처리되지 않게 한다 (PRG). |
| NFR-04 | 모든 화면 문구와 안내 메시지는 한국어로 한다. |
| NFR-05 | PC 브라우저 기준으로 만들되, 휴대폰 폭(360px)에서도 가로 스크롤 없이 읽을 수 있게 한다. |
| NFR-06 | 서비스 계층 규칙(중복 검사, 경기 검증, 전적 계산, 팀 나누기)은 자동 테스트로 검증한다. |

## 5. 데이터 모델

```
Player 1 ──── N MatchParticipant N ──── 1 Match
```

| 엔티티 | 필드 | 제약 |
|---|---|---|
| Player | id, name, riotId, mainPosition, subPosition, tier | riotId unique, name/riotId/mainPosition not null (tier는 예전 데이터 때문에 null 허용) |
| Match (테이블 `matches`) | id, playedAt(날짜), winner(BLUE/RED) | 모두 not null |
| MatchParticipant | id, match, player, team(BLUE/RED), position | 모두 not null |
